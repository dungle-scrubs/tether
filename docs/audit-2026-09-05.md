## High

### Scheduled-run identity (protocol, db.ts, service, HTTP, client-bridge)
**Smell:** Reconstructed meaning; parallel vocabularies.
**Evidence (rung 2):** The same identity (scope key + window start + window
end + task kind) has four shapes. `packages/protocol/src/task-contracts.ts:231-242`
(`ScheduledMaintenanceIdentity`, nested), `task-contracts.ts:311-315`
(`CandidateScheduleIdentity`), `packages/protocol/src/rest-schemas.ts:171-185`
(`scheduledTaskIdentitySchema`, flat, `scopeKey`), and
`apps/tether/src/db.ts:371-377` (`ScheduledTaskIdentityInput`, flat,
`scheduleScopeKey`). Hand conversions between them at
`http-task-route-handlers.ts:301-312` and `:548-559`,
`session-service-task-effects.ts:433-441`, `:489-498`, `:519-530`,
`db.ts:3893-3904`, and `packages/client-bridge/src/task-client.ts:107-124`
(7 sites; grep for `scheduleWindowStart:` finds them across 7 files).
`deriveScheduledTaskId` (FNV-1a) is the one place the identity is hashed,
so every conversion is a chance to hash a different tuple.
**Proposal:** One protocol-owned `ScheduledRunIdentity` type used verbatim
by REST bodies, service effects, and the db input, with a single
`scheduleColumns(identity)` / `identityFromRow(row)` pair inside `db.ts`.
**Payoff:** 7 conversions become 1; the hash input has one owner; the
client-bridge stops re-deriving field names (rung 2 count, rung 1 estimate).
**Churn:** 7 files, protocol minor bump; low risk because the wire shape can
stay and only the internal shapes collapse (rung 1).

### `apps/tether/src/config.ts` - two parsers for one contract
**Smell:** Reconstructed meaning; mirrored artifacts.
**Evidence (rung 4):** `readConfig` (`config.ts:72-166`, direct env parsing)
and `serverConfigDescriptor` (`config.ts:199-278`, Effect `Config`) each
encode every knob. Production uses only the descriptor via
`ServerConfigLive` (`server.ts`); `readConfig` is imported only by tests
(`test/config.test.ts` and siblings). Probe results: `PORT=abc` yields
`port=NaN` from `readConfig` and `3025` from the descriptor; `AUTH_MODE=disabledd`
throws in `readConfig` (`parseAuthMode`) and silently becomes `required`
in the descriptor (`Config.literal(...).pipe(Config.orElse(...))`). `PORT=-5`

**Proposal:** Delete `readConfig`; expose one `readServerConfig(env)` that
runs the descriptor synchronously (`Effect.runSync`) for tests and CLIs, and
add range validation for `PORT` and `DATABASE_POOL_MAX`.
**Payoff:** One place defines defaults and validation; config tests become
production evidence (rung 4 for the divergence, rung 1 for the payoff).
**Churn:** `config.ts`, `test/config.test.ts`, 3 CLI entry points that call
`readConfig` (rung 2).

### HTTP boundary (`http.ts`, `http-*-route-handlers.ts`, `http-route-inventory.ts`)
**Smell:** Pass-through arguments; callsite boilerplate; convention-enforced
consistency.
**Evidence (rung 2):** `handleHttp` (`http.ts:583-636`) and
`handleHttpRequest` (`http.ts:637-820`) take 17 positional parameters and
forward the same 7-field bag (`service`, `hub`, `auth`, `request`,
`response`, `url`, `requestId`) to every handler. Each handler file
re-implements method+regex dispatch by hand, e.g. `matchSessionResourceRoute`
(`http-session-route-handlers.ts:561-639`) and the task handler chain
(`http-task-route-handlers.ts:196-531`). `http-route-inventory.ts:7-25`
imports 7 route groups and omits `authTicketHttpRoutes`
(`http-auth-ticket-route-handlers.ts:11-18`), `browserPairingHttpRoutes`
(`http-browser-pairing-route-handlers.ts:22-35`), and
`browserOperatorHttpRoutes` (`http-browser-operator-route-handlers.ts:35-72`),
9 routes; `test/http-route-runtime.test.ts` checks only the fenced names, so
the omission is invisible.
**Proposal:** One `RouteContext` object and a route table keyed by the
existing `HttpRouteSpec` (`http-route-spec.ts`) whose entries carry the
handler; `handleHttpRequest` iterates the table. The inventory then *is* the
dispatcher and cannot drift.
**Payoff:** 10 handler files stop re-declaring the parameter bag and
dispatch; adding a route is one table row; D-4 disappears (rung 1).
**Churn:** 12 files, mechanical; medium risk only in preserving auth
ordering per route (rung 1).

# 2. Correctness and concurrency of the coordination core

What holds up (rung 3 traced, rung 4 where tests ran): control epochs are
strictly monotonic with the atomic fence in
`assertControlEpochCurrentWithClient` (`db.ts:1435-1480`); task claims use
`FOR UPDATE` on the task row and a claim generation fence
(`claimTaskWithEvent`, `db.ts:3308-3454`, reclaim emits `claim_expired` then
`claimed`); the sweeper uses `FOR UPDATE SKIP LOCKED` with a deadlock retry
(`expireTaskClaims`, `db.ts:2046-2135`); scheduled runs are serialized under
two advisory locks (`ensureScheduledRunWithEvents`, `db.ts:3889-4056`);
event sequences come from `session_event_sequences`; REST acquisition is
idempotent on Acquisition ID; replay windows are bounded and tested; the
e2e suite (188 tests) covers reconnect, reclaim, and multi-replica delete
refusal. The findings below are the gaps.

### C-1 High - `pg` Pool without an `error` listener crashes the process
**Evidence (rung 4):** `createPool` (`db.ts:277-287`) returns
`new Pool(...)` with no `pool.on("error")`. Run A of the probe: after
`docker stop` of Postgres the server printed `throw er; // Unhandled 'error'
event ... Emitted 'error' event on BoundPool instance` and exited. Node's
`pg` emits `error` on idle clients whose backend dies (failover, restart,
`pg_terminate_backend`, idle timeout at the proxy); with no listener the
emitter throws. Run B with a listener attached stayed up and `/ready`
returned 503.
**Fix:** Attach `pool.on("error", log)` in `createPool` and let readiness
report the outage.

### C-2 High - lock-order inversion between `deleteSession` and every FK-inserting path
**Evidence (rung 4):** `deleteSession` locks the session row first
(`SELECT ... FROM sessions WHERE session_id = $1 FOR UPDATE`, `db.ts:1827-1830`)
and then lease rows `FOR UPDATE` (`db.ts:1854-1863`). `claimControlLease`
(`db.ts:1014-1131`) locks lease rows `FOR UPDATE` first, then inserts a new
lease generation whose FK takes `KEY SHARE` on the session row. `FOR UPDATE`
conflicts with `KEY SHARE`. The probe replayed the delete's first statement
and ran the real `claimControlLease` concurrently: the claimant failed with
`40P01 deadlock detected`. `claimControlLease` has no deadlock retry, so the
WebSocket connect or REST acquisition fails. `acquireRestParticipantControl`,
`upsertParticipant`, and `insertTask` follow the same lease/task-then-FK
order. Delete is refused in multi-replica topology, but the lock is taken
before the eligibility check, so any delete request on a live session can
kill a concurrent reconnect in single-replica mode.
**Fix:** Lock the session row with `FOR NO KEY UPDATE` (compatible with
`KEY SHARE`) or take it after the lease and task locks, and add the same
`40P01` retry the sweeper has.

### C-3 Medium - malformed JSON yields 500
**Evidence (rung 4):** `readJsonBody` calls `JSON.parse`
(`http-route-runtime.ts:348-373`); the `SyntaxError` reaches
`handleHttpRouteError` (`:116-185`) and is logged and returned as
`500 Internal server error`. Probe: `POST /sessions` with `{not json`
returned 500.
**Fix:** Catch `SyntaxError` in `parseJsonBody` and respond 400
`invalid_json`.

### C-4 Medium - `/health` is not liveness
**Evidence (rung 4):** `http.ts:693-700` calls
`service.readScalabilityHealthWarnings()`, which runs the aggregate in
`session-scalability-diagnostics.ts:262-294` over all sessions and events.
With Postgres stopped, `/health` returned 500. `docs/multi-replica-runtime.md:34`
says "`GET /health` is liveness". A liveness probe that fails on a DB outage
makes orchestrators restart healthy replicas during a database failover,
and the unauthenticated full-scan is amplification.
**Fix:** Make `/health` return 200 with no I/O; move the warnings to `/ready`
or an admin-only diagnostics route.

### C-5 Medium - 500 logs drop the cause
**Evidence (rung 4):** `normalizeRouteError` (`http-route-runtime.ts:380-392`)
records only the outer error's name and message; run B's log line for the
DB-down request was `http.route_error ... "Session service persistence
failed during persistence"` with no `pg` code or message. The wrapper is
built at `session-service-runtime.ts:79`.
**Fix:** Serialize the `cause` chain (name, message, `code`) into the log
record, never into the response.

### C-6 Medium - invalid `runtimeKind` closes as an internal error
**Evidence (rung 3):** `participantRuntimeKindSchema.parse` at
`websocket-participant-gateway.ts:895-897` runs inside `Effect.try`; the
failure path reaches `socket.close(1011, "participant registration failed")`
(`:937`) or the generic 1011 at `:288`. A typo in a client query string
reads as a server fault and is logged as one.
**Fix:** Validate `runtimeKind` before registration and close with 1008
(policy violation) and a reason code.

### C-7 Medium - fanout scans are quadratic in sessions
**Evidence (rung 2):** `hasLocalSocket` (`session-event-fanout.ts:541-543`)
walks `hub.sessionCursors()` (an array of every session with a local
socket) on every notification and again per cursor in the poll loop
(`:396-413`). With N sessions per replica each poll costs O(N²).
**Fix:** Add `hub.hasSession(sessionId)` backed by the existing map.

### C-8 Medium - permanent delete loads the inventory
**Evidence (rung 2):** `http-session-route-handlers.ts:204` calls
`service.listSessions()` and searches the array for one id; `:167` does the
same for a read.
**Fix:** A `readSessionInventoryEntry(sessionId)` service method.

### C-9 Low - `claimControlLease` checks the session outside the transaction
**Evidence (rung 2):** `db.ts:1025` calls `requireSession` before the
transaction opens at `:1030`; a delete between the check and the insert
surfaces as an FK error instead of `SessionNotFound`.
**Fix:** Move the check inside the transaction after the session lock.

### C-10 Low - loose protocol validators
**Evidence (rung 2):** `packages/protocol/src/event-builders.ts:61`
`seq: z.number()` accepts floats and negatives; `records.ts:497-517`
validates some timestamps with `.datetime()` and others as plain strings.
**Fix:** `z.number().int().positive()` for `seq`; one timestamp schema.

### Multi-replica assumptions checked against `docs/multi-replica-runtime.md` and ADR 0001
- Delete refused when `RUNTIME_TOPOLOGY=multi`: implemented and e2e-tested
  (rung 4).
- Fanout catch-up staleness surfaces in `/ready`: implemented (rung 3).
- Host Presence is replica-scoped: implemented in `host-presence.ts`
  (rung 3).
- Operator command admission uses a single global advisory lock
  (`db.ts:2743`), which the doc does not mention; see S-9.

# 3. Security

### S-1 High - no documented way to obtain a working credential
**Evidence (rung 4 and 3):** README.md:114 and apps/tether/README.md:30
tell users to run `pnpm --filter tether mint ...`. `mint-cli.ts:51-68`
mints a legacy 2-segment token. `auth/enforcement.ts:332-347` rejects
legacy tokens unless `allowLegacyTokens`, whose default is `false`
(`config.ts:427-429`). The probe confirmed `auth_legacy_token_rejected`.
The durable path, `POST /auth/grants`, is gated by `issuanceEnabled:
authOptions.preEnforcementGrantIssuanceEnabled ?? false` (`http.ts:355`),
and `authRuntimeOptionsFromConfig` (`enforcement.ts:261-269`) never sets that
field, so production always answers 503 `auth_grant_issuance_gated`
(`http-auth-grant-route-handlers.ts:89-94`). The working entry point is
`bootstrap-admin` (`auth/bootstrap-cli.ts`), which requires
`AUTH_GRANT_BOOTSTRAP_COMPATIBILITY_CONFIRMED=true`; no document mentions
`bootstrap-admin`, `pair-browser`, `ensure-session`, or that env var (grep
across README, docs, CONTRACTS, SECURITY: 0 hits). A user following the
README either fails auth or sets `AUTH_ALLOW_LEGACY_TOKENS=true`, which
yields unrevocable 30-day tokens.
**Fix:** Add `AUTH_GRANT_ISSUANCE_ENABLED` to the config descriptor and
wire it to `preEnforcementGrantIssuanceEnabled`; rewrite the auth
quickstart around `bootstrap-admin` and `/auth/grants`, and mark `mint` as
legacy.

### S-2 Medium - permanent delete authorized as `session-create`
**Evidence (rung 2):** `http-session-route-handlers.ts:193` authorizes
`POST /sessions/{id}/delete` with action `"session-create"`;
`auth/authorize.ts:47-52` grants that to any non-observer role with service
scope. A participant runtime token with `*` scope can permanently destroy
archived sessions.
**Fix:** Authorize delete as `admin`.

### S-3 Medium - embedded dashboard cannot work with auth enabled
**Evidence (rung 3):** `http.ts:736-745` requires an admin bearer to serve
`/ui`, then calls `handleUiHttpRoute` a second time unconditionally at
`:743` (dead after the first returns). The page's `fetch(path, { headers:
{ accept } })` (`ui/sessions-dashboard-html.ts:226-230`) carries no
credential, so every data call returns 401 under `AUTH_MODE=required`.
**Fix:** Either serve the dashboard through the browser-operator cookie
session or document it as `AUTH_MODE=disabled` only; delete the dead branch.

### S-4 Medium - pairing rate limits keyed on the socket address
**Evidence (rung 2):** `http-browser-pairing-route-handlers.ts:168-171`
uses `request.socket.remoteAddress`; limits are 5 creates per 10 minutes
(`auth/browser-pairing-stores.ts:179`) and 20 failures per 10 minutes
(`:284`). No `trust proxy` or `X-Forwarded-For` handling exists. Behind a
reverse proxy every client shares one bucket (5 pairings per 10 minutes
for the whole deployment); when the address is `undefined` the key is
shared or skipped.
**Fix:** Add a `TRUSTED_PROXY_HOPS` setting and derive the client address
from it; fail closed when no address is available.

### S-5 Medium - `SameSite=Strict` cookie with a cross-origin allowlist
**Evidence (rung 2):** The operator cookie is set with `SameSite=Strict`
and the `__Host-` prefix (`http-browser-pairing-route-handlers.ts:56-63`);
`BROWSER_ALLOWED_ORIGINS` (`http-route-runtime.ts:33-39`) exists to admit
cross-origin browsers, and `packages/browser` sends `credentials: "include"`.
Browsers do not send Strict cookies on cross-site requests, so the allowlist
can never authenticate a browser client.
**Fix:** Decide: same-site only (drop the allowlist) or `SameSite=None;
Secure` with the CSRF header as the cross-site defense.

### S-6 Medium - runtime image
**Evidence (rung 4):** `apps/tether/Dockerfile:27-33` copies the whole
build tree (`COPY --from=build /repo ./`) with no `USER`; the built image
runs as uid 0 and contains `apps/tether/test`, sources, and 286 MB of
node_modules including devDependencies. The `deps` stage copies 4 workspace
manifests; pnpm 11 tolerated the missing worker and browser workspaces under
`--frozen-lockfile`, so the build passes today, but that tolerance is not
documented behavior.
**Fix:** `pnpm deploy --prod` into a runtime stage with `USER node`, and
copy all workspace manifests.

### S-7 Low - bearer in the query string
**Evidence (rung 2):** `enforcement.ts:161` accepts `access_token` from the
URL; both SDKs set it (`participant-runtime-client.ts:1816`,
`session-event-stream-client.ts:607`). Tokens land in proxy and access logs.
**Fix:** Prefer the single-use ticket path for WebSocket and log-redact
`access_token`.

### S-8 Low - `mint` TTL unbounded
**Evidence (rung 2):** default 30 days (`mint-cli.ts:7`), `--ttl` accepts
any value (`:103-117`); durable grants cap at 7 days.
**Fix:** Cap at the grant maximum or remove `mint`.

### S-9 Low - global operator-command admission lock
**Evidence (rung 2):** `db.ts:2743` takes
`pg_advisory_xact_lock("operator-command-admission","global")`; every
operator command in the deployment serializes on it.
**Fix:** Key the lock on session id.

### S-10 Low - CORS denial log spam
**Evidence (rung 2):** `http-route-runtime.ts:52-64` logs and answers every
request with a foreign `Origin` before authentication.
**Fix:** Sample or drop the log line; keep the 403.

### Config and secret handling (judged from source and tests, dotenv files not opened)
- Secrets are read only through the config descriptor (`config.ts`); config
  is never logged (rung 3).
- `.gitleaks.toml` allowlists test fixtures by path and the CI
  `secret-scan` job runs `gitleaks-action` with `fetch-depth: 0`, so history
  is scanned on every PR (rung 2). The history rewrite means the scan now
  starts from the new root.
- `AUTH_ISSUER` is required by the descriptor; the README does not say so
  (X-5).
